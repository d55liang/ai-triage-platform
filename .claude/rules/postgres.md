# PostgreSQL, SQLAlchemy & Alembic rules

## SQL

- **Always parameterise values.** Never interpolate user input into SQL with f-strings or `%`. Dynamic identifiers (column names) come only from an explicit allowlist.
- Use `RETURNING` on `INSERT` / `UPDATE` / `DELETE` to get the affected row without a second query.
- Select explicit columns, never `SELECT *`.
- Store IDs as `UUID` and timestamps as `TIMESTAMPTZ` (UTC); let the database set `created_at DEFAULT now()`.
- Table and column names are `snake_case`; tables are plural (`tickets`, `workflow_runs`).
- Add an index for every foreign key and for columns used in frequent `WHERE` filters.
- Paginate list endpoints before data grows (`LIMIT` / `OFFSET` or keyset).

## SQLAlchemy 2 (after the IAM migration)

- Use 2.0-style APIs only: `select()`, `Session.execute()`, `Mapped[...]` / `mapped_column()`. No legacy `Query` API.
- **ORM** for simple, routine CRUD on a single table. **Core** (`select()` with joins, aggregates, or `text()` with bound parameters) for complex or performance-sensitive queries.
- One engine per process, created in `app/database.py`. One session per request, provided via a FastAPI dependency, closed when the request ends.
- Repositories own transactions: commit on success, roll back on error. Services don't touch sessions directly.
- Repositories still raise `KeyError` for a missing row, so routers stay unchanged.

## Alembic

- Every schema change is an Alembic migration. Never edit the schema by hand in Aurora.
- Review autogenerated migrations before committing; autogenerate misses some changes (renames, server defaults, some constraints).
- Every migration has a working `downgrade()`.
- Never edit a migration that has already been applied to Aurora; add a new one.
- Run migrations against local PostgreSQL first, then against Aurora.
