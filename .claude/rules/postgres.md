# PostgreSQL, SQLAlchemy & Alembic rules

## SQL

- **Always parameterise values.** Never interpolate user input into SQL with f-strings or `%`. Dynamic identifiers (column names) come only from an explicit allowlist.
- Use `RETURNING` on `INSERT` / `UPDATE` / `DELETE` to get the affected row without a second query.
- Select explicit columns, never `SELECT *`.
- Store IDs as `UUID` and timestamps as `TIMESTAMPTZ` (UTC); let the database set `created_at DEFAULT now()`.
- Table and column names are `snake_case`; tables are plural (`tickets`, `workflow_runs`).
- Add an index for every foreign key and for columns used in frequent `WHERE` filters.
- Paginate list endpoints before data grows (`LIMIT` / `OFFSET` or keyset).

## SQLAlchemy 2 (after the IAM migration)

- Driver is psycopg 3 (`psycopg[binary]`, which bundles libpq). The URL scheme is `postgresql+psycopg://`, not `postgresql://`, which would select psycopg2.
- Use 2.0-style APIs only: `select()`, `Session.execute()`, `Mapped[...]` / `mapped_column()`. No legacy `Query` API.
- ORM table classes live in `app/models/orm.py` and inherit `Base` from `app/database.py`. Nullability comes from the annotation (`Mapped[str]` is `NOT NULL`, `Mapped[str | None]` is nullable). Timestamps need `DateTime(timezone=True)`; plain `Mapped[datetime]` creates `TIMESTAMP WITHOUT TIME ZONE`.
- **ORM** for simple, routine CRUD on a single table. **Core** (`select()` with joins, aggregates, or `text()` with bound parameters) for complex or performance-sensitive queries.
- One engine per process, created in `app/database.py`.
- **The caller owns the transaction.** HTTP requests get one session per request from `SessionDep` (`app/dependencies.py`), which wraps `get_session()` (`SessionLocal.begin()`: commit if the handler returns, roll back if it raises). Workers and scripts open their own with `with SessionLocal.begin() as session:`.
- `SessionDep` uses `Depends(get_session, scope="function")` so the commit runs before the response is sent. With the default `"request"` scope it runs after, and a failed commit would follow a success response.
- Repository functions take `session: Session` as their first parameter. They query, `add`, `delete` and `flush()`, but never open, commit, roll back or close a session. Call `flush()` when the response needs database-generated values (e.g. `created_at`) before the request commits.
- Services pass the session through to repositories and never use it directly.
- Don't make slow external calls (LLM, queue) while a session holds a connection; the pool is small.
- Repositories still raise `KeyError` for a missing row, so routers stay unchanged.

## Alembic

- Every schema change is an Alembic migration. Never edit the schema by hand in Aurora.
- Review autogenerated migrations before committing; autogenerate misses some changes (renames, server defaults, some constraints).
- Every migration has a working `downgrade()`.
- Never edit a migration that has already been applied to Aurora; add a new one.
- Run migrations against local PostgreSQL first, then against Aurora. (Exception so far: the first migration went straight to the empty Aurora database, checked with `--sql` and an upgrade/downgrade round trip, because no local PostgreSQL exists yet.)
- `alembic/env.py` uses the app's `engine` from `app/database.py` (IAM token, pinned TLS), so `sqlalchemy.url` in `alembic.ini` stays empty. Never put a URL or credentials there.
- `env.py` must import every module that defines tables (`import app.models.orm`). An unimported model is missing from `Base.metadata`, and autogenerate then proposes dropping its table.
- Changes to the allowed values of an enum `CHECK` constraint aren't detected by autogenerate; write that migration by hand (drop and re-create the constraint by its convention name, e.g. `ck_tickets_ticket_status`).
